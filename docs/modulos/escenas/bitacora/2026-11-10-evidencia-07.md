## Sub-paso 0 · Sonda de la API (investigador, sonnet, 2026-11-10)
- `DisplayConfigSetDeviceInfo(*const DISPLAYCONFIG_DEVICE_INFO_HEADER) -> i32` está en `windows` 0.60, junto con `GET_ADVANCED_COLOR_INFO` (9), `SET_ADVANCED_COLOR_STATE` (10) y sus structs. Fuente: https://raw.githubusercontent.com/microsoft/windows-rs/0.60.0/crates/libs/windows/src/Windows/Win32/Devices/Display/mod.rs (tag 0.60.0).
- **No** trae los tipos de 24H2: `GET_ADVANCED_COLOR_INFO_2` (15), `SET_HDR_STATE` (16) ni `DISPLAYCONFIG_ADVANCED_COLOR_MODE`. Se definen a mano con el layout de `wingdi.h`: https://raw.githubusercontent.com/mirror/mingw-w64/master/mingw-w64-headers/include/wingdi.h (`DISPLAYCONFIG_SET_HDR_STATE { header; UINT32 enableHdr:1; reserved:31 }`; `_INFO_2`: bits supported, active, reserved1, limitedByPolicy, hdrSupported (4), hdrUserEnabled (5), wcgSupported, wcgUserEnabled; después colorEncoding, bitsPerColorChannel, activeColorMode SDR 0 / WCG 1 / HDR 2). Valores del enum: https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ne-wingdi-displayconfig_device_info_type (página del 2025-05-21; el 15-17 lo lista sin número, el número sale de mingw).
- Tamaños fijados al compilar en `acciones.rs`: encabezado 20, pedido 24, info_2 36. Si no dan, no compila.
- NO VERIFICADO en la sonda: qué devuelve `SET_HDR_STATE` en un Windows de antes de 24H2 y qué devuelve un SET sobre una pantalla sin HDR (la doc solo lista códigos genéricos: https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-displayconfigsetdeviceinfo). Por eso decide la re-lectura y no el código.
- Fuente única para 15/16 y los bits de `_INFO_2`: el espejo mingw-w64 (no oficial). Habría que cotejarlo con el `wingdi.h` del Windows Kits; en esta PC no está.

## Qué se hizo
1. **Datos** (`vendor/monarch/src/model.rs`, `displays/escenas.rs`): `ActionV2::Hdr { pantalla: String, prender: bool }`, tag `hdr` del contrato. `pantalla` va como texto en el vendor: un id tocado a mano se lee igual y no vuelve corrupto el `displays.json`. No entra en las listas viejas (`a_accion` → `None`). `save_scene` lo guarda con el id normalizado por `format_display_id(parse_display_id(..))`; mal formado → el error de `parse_display_id` (contrato :52). Se fue el "esta versión todavía no sabe guardar acciones hdr".
2. **Ejecución**: la lógica en `displays/hdr.rs` (pura, la prueba `displays-tests`): busca la pantalla entre las prendidas (id exacto → único EDID → sin EDID, mismo target en una sola placa, la regla del motor); apagada, no conectada o ambigua → se saltea con log; sin lectura o sin soporte → log; ya estaba → no toca; pide con la llamada nueva y re-lee (hasta 2 s, de a 250 ms); si no quedó, la vieja y re-lee; si tampoco, `HDR no cambió en <pantalla>`. El código de Windows va solo al log. Las llamadas de Win32 viven en `displays/acciones.rs` (`HdrDeWindows`, al lado del resto de las acciones reales), porque `displays-tests` no tiene el crate `windows`. `cola.rs`: el `Ejecutor` suma `hdr`; corre en su lugar de la fila. `mod.rs`: solo `mod hdr;`.
   - Lectura: en 24H2, `GET_ADVANCED_COLOR_INFO_2` (soporta = bit 4; prendido = interruptor "Usar HDR" (bit 5) o modo activo HDR); si ese Windows no la conoce, `GET_ADVANCED_COLOR_INFO` (bits 0 y 1, mismo molde que `apply.rs`).
